# Plan: GPUI migration, phase P1 core

Date 2026-11-09. Issue [#280](https://github.com/hpagniez/grace/issues/280), under [#278](https://github.com/hpagniez/grace/issues/278). Spec: the [migration guide](../specs/2026-11-08-gpui-migration.md) (Architecture, R1.4, R1.5, R3, R5.3, R6.1, feature map P1), [ADR 0031](../decisions/0031-move-grace-to-rust-and-gpui.md). Checklist: [parity](../specs/2026-11-08-gpui-migration-parity.md), the unit test rows of `src/main` and `src/shared`, and the JM and JJ scenarios.

P1 moves everything of Electron Grace that has no window into `crates/grace-core`: the model, the Karate command line, the run and its events, the data on disk. It ends when a headless run of the bench's 2,000-test project from `grace-core` alone writes the same `run.json` as Electron Grace. Nothing in P1 opens a window, and the Electron app does not change.

## Scope

The P1 rows of the feature map, by file:

| Electron Grace | `grace-core` | PR |
|---|---|---|
| `src/shared/{model, status, tags, env, threads, history, flaky, trends, http, events, theme, version, updates}.ts` | `model::*` | 1 |
| `karate/{command, argfile, process, environments}.ts` | `karate::{command, argfile, process, environments}` | 2 |
| `karate/{events, tree, run-state, steps, http}.ts`, `batch.ts` | `karate::{events, tree, run_state, steps, http}`, `batch` | 2 |
| `settings.ts`, `recent.ts`, `window.ts`, `secrets.ts`, `mask.ts`, `propertiesFile.ts` | `settings`, `recent`, `window`, `secrets`, `mask`, `properties_file` | 3 |

| `runner.ts`, `vendor.ts` and the runner tests of P1's features | `runner`, `vendor`, the `grace-run` example | 4 |

The other files of `src/main` port with the phase whose feature they serve, as the feature map says: `editor.ts` and `report-zip.ts` in P3; `karate/{maven, pom, libraries, compiled, subfolders, debug}.ts`, `watch.ts` and `runner.{debug, editor, libraries, pom, setup, subfolders, watch}.test.ts` in P4; `updates/*` in P5. Their rows stay open until then. The issue's exit check reads "every `src/main` and `src/shared` row"; this plan reads it as every row of a P1 module, since porting the updater before the views that drive it would guess at seams that do not exist yet (the same reason P0 left the dialog seams for their first caller). `src/shared/ipc.ts` has no test and no port: GPUI Grace has no IPC. `sanity.test.ts` checks that Vitest runs: `n/a`.

## Porting rules

Every PR of P1 follows these, so the five land as one crate:

1. **One module per file, test for test.** `src/main/x.ts` becomes `crates/grace-core/src/x.rs` (snake case), its Vitest file the `#[cfg(test)] mod tests` at its foot, one `#[test]` per `it`/`test`, named as the test in snake case (`"keeps the order"` → `keeps_the_order`), a `describe` as a nested `mod`. A test may merge or split only when the PR says why (guide R3.4). A test that checks only Node, Electron or IPC plumbing is `n/a` in the parity list with the reason.
2. **Same fixtures.** `test/fixtures/events/` and `test/fixtures/projects/`, read through `env!("CARGO_MANIFEST_DIR")`; never copied. A test that writes copies a fixture into its own `tempfile::TempDir`, so test files run in parallel (ADR 0020).
3. **Same files.** Every JSON file Grace writes keeps Electron Grace's keys, camelCase, through `serde`: `Option` that is `null` in TypeScript stays `null`; an optional `?:` key is `skip_serializing_if`. JavaScript numbers that are times or durations are `f64` through `model::js_num`, so `1700000000000` is not written `1700000000000.0`. Parsers of untrusted input (a file, the window) work on `serde_json::Value` and keep each rule of the TypeScript validator.
4. **Same strings.** The Karate command line, the argument file, notices and labels stay byte for byte (guide R1.2, R1.5). Where TypeScript counts a string's `length`, Rust counts UTF-16 units (`encode_utf16().count()`); JavaScript's default `sort()` compares UTF-16 units, `localeCompare` does not, and each port says which it keeps. JavaScript regular expressions port to `regex` with their flags; `\s` and `\d` keep JavaScript's meaning.
5. **Platform seams.** What differs by platform is one function with a test on each (guide R5.3): DPAPI on Windows, the Secret Service on Linux (secret properties are refused with a notice when there is none); `taskkill /T /F` on Windows, the process group on Linux; the Windows below-normal priority and the job object are no-ops on Linux.
6. **Light.** No timer, thread or poll that outlives a run (ADR 0030). Dependencies are already in `Cargo.lock` through GPUI where they can be (`serde`, `serde_json`, `regex`, `indexmap`, `sha2`, `windows`), pinned as the lock has them, and each PR that adds one says its size.
7. **Checks.** `cargo fmt --all`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo test -p grace-core`. Tests that start Java are real (guide R6.1): on Linux they use the `java` on `PATH` and the pinned `vendor/karate.jar`, on Windows the bundled JRE.
8. **Parity.** Each PR ticks its rows: the Proof column names the Rust module's tests (`grace-core::karate::command::tests`, 46 of 46).

## PR 1: the model

`model::*`, the port of `src/shared`: the tree, statuses, tags and the filter, environments and run properties, threads, the history record and its labels, flaky and trends views, HTTP calls and Copy as cURL, the event types, theme, versions and releases. Its types are what every later PR builds on, so it lands first. Adds `serde`, `serde_json`, `regex`, `indexmap` (all in the lock already) and `tempfile` for tests.

## PR 2: Karate

1. The command line first (guide R1.5): `command.rs` and `argfile.rs` on the same expected strings as `command.test.ts` and `argfile.test.ts`, then `process.rs`: spawn without a shell, the environment cleaned, `-Dstdout.encoding=UTF-8`, the memory cap and JIT flags (JM-01, JJ-01, JJ-02), below-normal priority, a job object on Windows that the updater's script can break away from, `taskkill /PID <pid> /T /F` to cancel.
2. `environments.rs`: the environments a project names.
3. The run's events: tailing `karate-events.jsonl` (`events.rs`), the dry run's tree (`tree.rs`), the run's state (`run_state.rs`), steps and HTTP calls from step text (`steps.rs`, `http.rs`), and `batch.rs`, one update per tick.

## PR 3: the data

`settings.rs` (every key of `settings.json`), `recent.rs`, `window.rs`, `secrets.rs` (DPAPI for the current user on Windows; old `safeStorage` values are not read, R5.4), `mask.rs`, `properties_file.rs`; then `history.rs` (one folder per run, 20 runs, ADR 0010), `flaky.rs`, `fingerprint.rs`, `trends.rs`. Same data folder (`paths::data_dir`), same file formats.

## PR 4: the runner and a headless run

1. `runner.rs`: the `Runner` of `runner.ts` without the window: open a project, dry run, run anything, cancel, environments and properties, tags, threads, history, re-run and re-run failed, flaky, trends, fingerprint. It reports `AppEvent`s to a callback, which the `Grace` entity of P2 will hold. The parts that need P4's modules (Maven and Gradle libraries, the pom, sub-folders, watch, the debugger) wait for P4.
2. `runner.*.test.ts` of P1's features, real Java and Karate: discovery, runs, env, properties, tags, threads, history, rerun, fingerprint, flaky, trends, home.
3. `examples/grace-run.rs`: opens a folder, runs everything with the settings in the data folder, and leaves the run folder (`run.json`, the report) in the data folder, as Electron Grace does. No window.
4. The exit check below, recorded in `docs/checks/`.

## Exit check (from #280)

Every P1 row of the parity list ported or `n/a`, and a headless run of the bench's 2,000-test project (`e2e/big-project.ts`) from `grace-core` alone writes the same `run.json` as Electron Grace: the same keys, the same tests in the same order with the same statuses, `selection`, `filter`, `threads`, `env`, `outcome` and `exitCode`; only `startedAt`, `durationMillis`, each `durationMillis` of a test and `fingerprint` (the files' times) may differ. On Linux in CI against a `run.json` Electron Grace wrote on Windows, and once on the owner's PC with the bundled JRE, with his go-ahead.

## Cost

P1 ships nothing: the Electron app is unchanged and GPUI Grace has no views yet. What it adds:

- **The app, later.** `grace-core` is plain Rust; its dependencies are already built for GPUI, so `Grace.exe` grows only by Grace's own code, well under 1 MB. The runner holds what Electron Grace's main process held (the tree, the run state, the last run's steps and calls) without a JavaScript heap.
- **Idle.** No timer, poll or thread while no run is going: tailing the events file and reading Java's output live only as long as the run (ADR 0030).
- **During a run.** One thread reads Java's output, one tails the events file; their updates are batched per tick as `batch.ts` does.
- **CI.** `cargo test -p grace-core` adds a few seconds of build and, for the runner tests, Java runs as long as the Vitest runner tests take today. Linux CI gets the Karate jar (pinned, checked against `scripts/vendor.json`) and a Java 21.
