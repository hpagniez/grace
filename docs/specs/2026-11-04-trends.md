# Trends

Date 2026-11-04. Status: draft. Covers [#93](https://github.com/hpagniez/grace/issues/93) (old F42).

## Intent

The History tab lists the stored runs one by one. It does not say whether the suite, a folder or one test is getting worse: failing more often, or slowing down. Trends draw that from the run history Grace already keeps (spec [run history](2026-10-25-run-history.md)), at the top of the History tab, for whatever the tree has selected.

Who: someone who runs the same tests all day and wants to see at a glance whether a part of the suite slips, without opening twenty reports.

## Goals, non-goals, anti-goals

- Goal: per stored run, the pass rate and the time per test of the selection (the whole suite with nothing selected), in a strip that reads in one look.
- Non-goal: keeping more than the 20 runs history keeps (`HISTORY_LIMIT`). The strip reads whatever history holds; a longer history is its own issue and a decision record.
- Non-goal: the run's wall-clock duration as a trend. The History table already shows it per run, and it only compares between runs that ran the whole selection with the same thread count.
- Anti-goal: any cost while the History tab is closed, or while nothing changes. Grace runs lightly first ([ADR 0023](../decisions/0023-run-lightly-as-a-release-requirement.md)).
- Anti-goal: a chart library, SVG plumbing or animation for twenty columns.

## Approaches

Each test's status and duration are in the run's `run.json`, read by the main process. The window gets only per-run counts (`HistoryEntry`).

1. **The window asks main when it needs a trend (chosen).** While the History tab shows, the window asks main for the trend of the selection when the tab opens, the selection changes, the history changes or the tree changes. Main reads the stored runs, matches their tests to the current tree, and answers with at most 20 small points. Nothing is computed or held while the tab is closed.
2. Main sends each test's result with every `history` event, and the window computes any selection's trend at once. The window then holds 20 × the test count all day, used or not.
3. Main computes a trend for every node after each run and tree change, as it does for flaky marks. CPU at every run's end and memory per node, for a view nobody may open.

The owner chose 1: it is the only one that costs nothing while History is closed.

## Requirements

### R1. Where

1. The trend strip shows at the top of the History tab, above the runs table, while the history has at least one run. With no run, the tab shows its empty state as today, with no strip.
2. The strip follows the tree selection, as the HTTP tab does: with nothing selected it covers every test of the tree; with a folder, feature or outline selected, the tests under it; with a scenario or row selected, that test.
3. Its caption names what it covers: "All tests" with nothing selected or the root selected, else the selected node's label as the tree shows it (a feature's file name, a scenario's name).
4. The strip is the first thing in the History tab's scroll, above the table: scrolling the table moves the strip out of view, and the table's sticky header then sticks as today. A short panel keeps its table rows reachable. The strip is about 76 px tall: an 8 px padding, a caption line, then the two rows of R3.

### R2. Which runs, which tests

1. The strip reads the runs history lists (newest 20) that ran on the environment picked now (none: the runs with none), left out: a step debugger run (`debug: true`), whose durations include the pauses. A trend is per environment, as flaky proof is: switching the environment switches the strip.
2. A stored test counts for the selection when it matches a test of the current tree, by the rule flaky detection uses (`resolveNode`): the same key with the same name, else the one test in the whole tree of the same file, kind and name; and that test is under the selection. So a folder counts what its children count.
3. Only a test stored as `passed` or `failed` counts. `notRun` and `interrupted` do not.
4. A run with no counted test for the selection has no column: a Re-run failed of other tests, or a run of another folder, leaves the selection's strip alone. A cancelled run, or one that stopped on an error (exit 3), counts the tests that finished before it stopped, like any other.
5. The columns are the remaining runs in start order, oldest on the left, newest on the right, evenly spaced: a weekend between two runs takes no room.
6. With history but no run counting for the selection, the strip keeps its height and says "No stored run ran these tests" in muted text.

### R3. What a column shows

Each run has one column, made of two parts that share its place on the x axis.

1. **Pass rate**, the upper row, 24 px tall: a bar the full height of the row. Its lower part, in the passed colour, is the share of counted tests that passed; its upper part, in the failed colour, the share that failed. A share of 0 draws nothing. Between two drawn parts, a 2 px gap in the surface colour. For one selected test the bar is all passed or all failed.
2. **Time per test**, the lower row, 24 px tall, 4 px under the first: a bar whose height is the mean `durationMillis` of the counted tests that have one, scaled so the tallest column of the strip fills the row; a non-zero value is at least 2 px tall. A run whose counted tests have no duration has no time bar; its pass-rate bar stays.
3. Bars are 12 px wide with 4 px of air between columns, rounded 4 px at the top and square at the baseline. Each row sits on a 1 px baseline in the line colour. No gridlines, no axis ticks on x.
4. Left of the rows, a label and the newest column's value: "Pass rate 92%" and "Time per test 1.40 s". With one selected test, "Passed" or "Failed" instead of a percentage. A percentage is rounded down, so a run with one failure in 300 reads 99%, never 100%. Times use the step format, "120 ms" under a second, else "1.40 s".
5. Right of the time row, in muted text, the value of its tallest column: the top of its scale.
6. Colours only through the semantic tokens: `passed` and `failed` for the pass rate (with the gap and the fixed order, passed always below, the two never rely on hue alone), `muted` for time, `line` for baselines, `surface` for the gap. No new token. Both themes come from the tokens.

### R4. Reading a column

1. Each column is a button. Its name, also its tooltip (`Tooltip`, where it places itself), is one line: when it ran (`whenLabel`), then the counts, then how many of the selection's tests it ran, then the time per test, e.g. "Today 14:32: 12 passed, 3 failed, 15 of 412 tests, 1.40 s per test". For one selected test: "Today 14:32: passed, 1.40 s". A part with no value is left out.
2. A click on a column, or Enter or Space on it, scrolls that run's row of the History table into view. Focus stays on the column.
3. The strip is a group named by its caption, e.g. "Trend of All tests", so a screen reader says what it covers before the columns.

### R5. When it is worked out

1. The window asks main for the trend of the selection when the History tab shows, and again when the selection, the history, the tree or the environment changes while it shows. Main uses the environment it holds.
2. At most one request is in flight. A change that comes while one is in flight is asked for once that one answers, with the selection then current; answers to a request older than the newest are dropped.
3. While the History tab is not shown, nothing is asked and nothing is held: the strip leaves with the tab.
4. Main answers from disk each time and keeps nothing between requests. A request with no open project, no tree, or a key that is not a node of the tree, gets no points.
5. Main checks the request: a key is a string of at most 1000 characters starting with a node prefix, or null for the whole tree; anything else gets no points.

## Cost

- **Idle:** nothing. With History closed the strip is not mounted. With History open and nothing changing, no request, timer, poll, observer or animation. No transition on the bars.
- **A request:** main reads the up to 20 `run.json` files that it already reads at the end of every run (`listRuns`), builds one key index of the tree (one walk of its nodes), and makes one pass over the stored tests: 20 × tests lookups. A project of 500 tests stores about 100 KB of records in all: a few milliseconds. A project of 5,000 tests stores about 1 MB per record: about 100–200 ms of main-process time per request, during which IPC waits; the window keeps painting. R5.2 bounds it to one request at a time, so holding an arrow key in the tree never queues more than one.
- **Memory:** the window holds at most 20 points of seven numbers and an id, under 2 KB, only while History shows. Main holds nothing between requests.
- **Painting:** at most 20 buttons of three boxes each, drawn once per answer.
- **Start and size:** nothing at start. About 5 KB of code. No dependency.

## Design decisions already made

The builder's calls, open to the owner's correction:

- Plain HTML boxes styled with Tailwind token classes, not SVG: each column is a button that the house `Tooltip`, focus ring and themes already serve, and `palette.test.ts` checks its classes like any other.
- Time uses the `muted` token, not a new one: a single neutral series needs no hue of its own, and grey keeps it apart from the passed and failed colours above it. (In the conversation a new token was proposed; the existing grey does the job.)
- A run on another environment is left out (R2.1), the owner's call: dev and prod fail for different reasons, and the tree, discovered per environment, may lack another one's tests.
- Debug runs are left out (R2.1): their durations include the time paused at breakpoints, which would read as a slow-down.
- Matching to the current tree uses `resolveNode`'s rule (R2.2) through an index built once per request: `resolveNode` itself walks the whole tree per call, which is 20 × tests walks.
- No ambiguity guard like flaky's "stored twice" rule: a test that two stored tests could match only shifts a count, where for flaky it would brand a test.
- A click scrolls to the run's row (R4.2): the column needs a button for focus and the tooltip, and finding the run in the table is the next thing a person wants, to open its report.
- The strip's caption and the History table stay separate: the table keeps listing every run, whatever the selection.
- The strip scrolls with the table (R1.4) rather than staying fixed above it: at the panel's default 192 px a fixed strip would leave two table rows, and none at its 96 px minimum.
- The tooltip goes where `Tooltip` puts it by default, below the column: `Tooltip` has no "above" side, and a passing tooltip over the table rows hides nothing for long.
- Cancelled and exit-3 runs count their finished tests (R2.4): a test that finished passed or failed for real.
- The caption uses the tree's own row label, so a feature reads as its file name, as in the tree.

## Acceptance criteria

```gherkin
Feature: Trends

  Background:
    Given a project is open in Grace
    And the History tab is shown

  # R1
  Scenario: No runs, no strip
    Given the project has no stored run
    Then the History tab shows "No runs yet. Runs appear here when they finish."
    And no trend strip shows

  Scenario: The strip covers every test with nothing selected
    Given three stored runs of the whole suite
    And nothing is selected in the tree
    Then the trend strip shows above the runs table
    And its caption reads "All tests"
    And it has three columns

  Scenario: The strip follows the tree selection
    Given stored runs of the whole suite
    When I select the feature "users.feature" in the tree
    Then the caption reads "users.feature"
    And each column counts only the tests of "users.feature"

  # R2
  Scenario: A run that did not run the selection has no column
    Given a run of the whole suite, then a run of "orders.feature" only
    When I select "users.feature"
    Then the strip has one column

  Scenario: A Re-run failed counts only the tests it ran
    Given a run of 10 tests with 3 failed, then a Re-run failed where 2 of the 3 passed
    And nothing is selected
    Then the newest column's tooltip reads "…: 2 passed, 1 failed, 3 of 10 tests, …"

  Scenario: Only runs of the picked environment count
    Given a run of the whole suite on "dev", then one on "qa"
    And "dev" is the picked environment
    Then the strip has one column, the "dev" run's
    When I pick "qa"
    Then the strip has one column, the "qa" run's

  Scenario: A debug run has no column
    Given a run of the whole suite, then a debug run of one scenario
    When I select that scenario
    Then the strip has one column

  Scenario: A selection no stored run ran
    Given stored runs of "orders.feature" only
    When I select "users.feature"
    Then the strip reads "No stored run ran these tests"

  Scenario: Columns run oldest to newest
    Given runs on Monday, Tuesday and Friday
    Then the leftmost column is Monday's and the rightmost Friday's
    And the three columns are evenly spaced

  # R3
  Scenario: Pass rate splits passed below and failed above
    Given a run where 3 of 4 counted tests passed
    Then its pass-rate bar is three quarters passed colour at the bottom and one quarter failed colour on top

  Scenario: One selected test is all passed or all failed
    Given a scenario that passed in one run and failed in the next
    When I select it
    Then the first column is all passed colour and the second all failed colour
    And the label reads "Pass rate Failed"

  Scenario: The newest value is rounded down
    Given the newest run passed 299 of 300 counted tests
    Then the label reads "Pass rate 99%"

  Scenario: Time per test is the mean of the counted tests
    Given the newest run counted two tests of 1 s and 2 s
    Then the label reads "Time per test 1.50 s"
    And the tallest time bar fills its row and its value shows at the right

  # R4
  Scenario: A column's tooltip names the run
    When I rest the pointer on the newest column
    Then a tooltip reads "Today 14:32: 12 passed, 3 failed, 15 of 412 tests, 1.40 s per test"

  Scenario: A click on a column finds its run in the table
    Given more runs than the table shows without scrolling
    When I click the oldest column
    Then the oldest run's row of the table is in view

  # R5
  Scenario: A finished run updates the strip
    Given the strip has two columns
    When a run of the whole suite finishes
    Then the strip has three columns

  Scenario: Nothing is worked out while History is closed
    Given the Console tab is shown
    When I select tests in the tree and a run finishes
    Then the window asks main for no trend

  Scenario: Selecting fast asks once at a time
    When I move the tree selection down five rows quickly
    Then at most one trend request is in flight at any time
    And the strip ends on the last selected row's trend
```
