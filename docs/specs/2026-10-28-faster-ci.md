# Faster CI

Date 2026-10-28. Status: approved. Covers [feature](../features.md) F44. Decision: [ADR 0016](../decisions/0016-windows-tests-in-parallel-jobs.md).

## Intent

The `test` workflow runs every unit and e2e test in one Windows job, one suite after the other. A ready PR waits about 20 minutes for it, a draft PR about 8.5. Agents push many PRs a day and wait for each. The [research note](../research/2026-10-27-ci-test-speed.md) measured where the time goes: `src/main/runner.test.ts` takes 422 s of the 468 s unit step, the e2e step takes 11 minutes, and on the private repo's 2-CPU runner the Java tests are CPU-bound, so more workers on one VM barely help.

Run the suites on more VMs instead: unit and e2e as separate jobs, each split in two. Target: a ready PR in about 7 minutes, a draft PR in about 5, for about 3 more billed Windows minutes per ready run.

## Who and what success looks like

The maintainer and the agents who open PRs.

Success:
- An agent marks a PR ready for review. About 7 minutes later `test` is green, with four jobs: `unit (1)`, `unit (2)`, `e2e (1)`, `e2e (2)`.
- A push to a draft PR gets its unit result in about 5 minutes. Both e2e jobs skip the step named `e2e`.
- A PR with the `merge-when-green` label merges only once every `e2e` step of its `test` run has passed.
- The same tests run as before: the four jobs together run every unit test file and every e2e test exactly once.

## Goals, non-goals, anti-goals

**Goals:** the behaviour in the Requirements section below.

**Non-goals:**
- Leak checks scoped to each test, so Java test files could run in parallel on one machine (research note 3.4). A local speed-up, not needed for CI once each job has its own VM.
- A cheaper JVM start (class-data archive, research note 3.5).
- A shorter sleep in the `clean` fixture.
- Exactly even halves. Playwright shards by test count, not time; the first CI run shows how far apart they are.
- Caching the packaged app between the e2e halves. Each half packages it again (about 25 s).

**Anti-goals** (failure even if everything else works):
- A test file or e2e test that no job runs, or that two jobs run.
- A test whose assertions changed to make the split work.
- A PR merged by `merge-when-green` while one e2e half failed or skipped.
- Two suites' Java processes on one VM, so a global leak check sees another job's Java.

## Constraints

- Windows minutes are the scarce budget ([ADR 0007](../decisions/0007-github-actions-ci-cd-on-the-free-private-plan.md)): about 1,000 a month. Billing rounds each job up to a whole minute.
- `merge-when-green.yml` runs as it is on `develop` (`workflow_run`, `pull_request_target`), so its change takes effect only after this PR merges.
- Vitest 5.0.5: the CLI `--exclude` does not reach inline `projects` (checked: `vitest list --exclude src/main/runner.test.ts` still lists it, with or without `extends: true`). Positional file filters do.
- Playwright 1.64.1 shards whole files when `fullyParallel` is off. It splits by test count, files in name order (`filterForShard`). The only weights are the internal `PWTEST_SHARD_WEIGHTS` variable; do not use it.
- The draft flag in the `pull_request` event is stale when a push and "ready for review" land together, so the `e2e` job asks the API (as today).

### What exists today

- `.github/workflows/test.yml`: one job `test`, `timeout-minutes: 40`: setup, `npm test`, the draft check (step `pr`), then the step named `e2e` (`npm run e2e`) unless the PR is a draft.
- `merge-when-green.yml:68` reads `[.jobs[].steps[] | select(.name == "e2e")][0].conclusion`: only the first `e2e` step.
- `vitest.config.mts`: `fileParallelism: false`, projects `node` (`**/*.test.ts`) and `dom` (`**/*.test.tsx`), a shared `exclude` list.
- `src/main/runner.test.ts`: 2,446 lines, helpers at the top and before "Runner history", nine `describe` blocks, one `afterEach` that disposes runners and removes temp folders.
- `package.json`: `"e2e": "npm run package && npx electron --version && playwright test"`. Arguments after `npm run e2e --` reach `playwright test`.

## Requirements

### R1. Two jobs (research note 3.1)

1. `test.yml` has a `unit` job and an `e2e` job, both `windows-latest`, both with today's setup steps: checkout, setup-node with npm cache, the Electron cache, the `vendor/` cache, `npm ci`, `npm run vendor`.
2. `unit` runs the unit tests. `e2e` runs the draft check and then the step named `e2e`, skipped on a draft PR, as today.
3. Each job has `timeout-minutes: 20`.
4. The comments in `test.yml` and the workflow table in `AGENTS.md` describe the jobs.

### R2. The runner tests in one file per block (research note 3.2)

1. `src/main/runner.test.ts` becomes nine files, one per `describe` block: `src/main/runner.<part>.test.ts` with parts `discovery`, `runs`, `tags`, `threads`, `env`, `properties`, `history`, `flaky`, `home`.
2. The helpers used by more than one block move to `test/runner.ts`. The `afterEach` cleanup becomes an exported function that each file passes to `afterEach`.
3. Each test keeps its name, its body and its assertions. Only imports change.
4. The split runs the same tests: the nine files together have 120 tests, as `runner.test.ts` had.

### R3. Unit tests in two halves (research note 3.2)

1. `unit` is a matrix of two, `half: [1, 2]`.
2. `test.yml` holds one list: the runner files of half 2, `discovery`, `runs`, `tags`, `env` and `properties` (about 200 s on CI). Half 2 runs only those files, as positional filters to `npm test`. Half 1 runs every other test file (about 185 s), by excluding the list. The research note's split also had `threads` in half 2; the first CI run of the F44 PR showed half 1 at 155 s and half 2 at 230 s, so `threads` (31 s) moved to half 1.
3. `vitest.config.mts` adds the paths in the environment variable `UNIT_EXCLUDE` (space-separated) to the `exclude` of both projects. With the variable unset, `npm test` runs every file, as today.
4. `fileParallelism: false` stays.

### R4. E2E tests in two shards (research note 3.3)

1. `e2e` is a matrix of two, `shard: [1, 2]`. Its step named `e2e` runs `npm run e2e -- --shard=<shard>/2`.
2. Playwright's `workers: 1` stays.

### R5. Merge only when every e2e half passed

1. `merge-when-green.yml` merges only when the `test` run has at least one step named `e2e` and every such step has the conclusion `success`.

### Rebalancing later

If one half of a pair takes much longer than the other on CI, move runner files between the half-2 list and half 1 in `test.yml`. For e2e, rename or split spec files: Playwright assigns files in name order by test count. Check the step times in the job logs.

## Acceptance criteria

```gherkin
Feature: Faster CI

  Scenario: a ready PR runs four jobs
    Given a PR into develop that changes more than docs
    When it is marked ready for review
    Then the test workflow runs the jobs "unit (1)", "unit (2)", "e2e (1)" and "e2e (2)"
    And each job runs on its own windows-latest VM
    And both e2e jobs run the step named "e2e"

  Scenario: a draft PR runs unit tests only
    Given a draft PR into develop that changes more than docs
    When a commit is pushed
    Then both unit jobs run their tests
    And both e2e jobs skip the step named "e2e"

  Scenario: every test runs exactly once
    Given the half-2 list in test.yml
    When the test files of "unit (1)" and "unit (2)" are listed
    Then together they hold every file that "npm test" runs
    And no file is in both
    And the runner files together have 120 tests

  Scenario: the e2e shards cover the suite
    When "playwright test --list --shard=1/2" and "--shard=2/2" are run
    Then together they list every test that "playwright test --list" lists
    And no test is in both

  Scenario: npm test still runs everything locally
    Given UNIT_EXCLUDE is not set
    When "npm test" runs
    Then it runs every unit test file

  Scenario: no assertion changes
    When the diff of the runner test split is read
    Then every test name, body and assertion is the same as in runner.test.ts

  Scenario Outline: merge-when-green and the e2e steps
    Given a PR labelled merge-when-green with checks green and a successful test run
    And the run's e2e steps have the conclusions <conclusions>
    When merge-when-green runs
    Then the PR <outcome>

    Examples:
      | conclusions          | outcome           |
      | success, success     | is merged         |
      | success, skipped     | is not merged     |
      | skipped, skipped     | is not merged     |
      | none                 | is not merged     |

  Scenario: the time goal
    When the PR of this feature is ready and its test run is green
    Then a check record in docs/checks holds each job's step times
    And compares them with the research note's estimates
```
