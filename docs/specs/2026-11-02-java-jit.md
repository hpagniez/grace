# Java's JIT

Date 2026-11-02. Status: approved. Covers [#179](https://github.com/hpagniez/grace/issues/179).

## Intent

Most of the CPU the bundled Java (Temurin 21) spends while Grace lists or runs tests goes to compiling Karate's own code, not to the tests. Java compiles in two tiers: C1 compiles hot code quickly, then C2 compiles the hottest code again, slowly, into faster code. By default it gives C2 two thirds of a pool of compiler threads that grows with the machine: 12 threads in all on the 16-thread reference machine, 4 on 8 threads. A dry run or a short run ends before most of C2's work pays back. Grace stays open all day beside IDEs, browsers and containers, and running lightly comes first, then speed ([ADR 0023](../decisions/0023-run-lightly-as-a-release-requirement.md)): Java should spend its CPU on the tests.

## What the measurements show

Measured on the reference machine (Windows 11 Pro, Ryzen 7 5800X, 16 threads, 32 GB), Karate 2.1.4 started the way Grace starts it, heap flags included, without the app. Projects: the bench's 2,000- and 10,000-test ones (`e2e/big-project.ts`), and a suite of 1,000 scenarios whose steps are mostly Karate's own JavaScript (a loop of 300,000 turns, lists of 2,000 objects filtered, mapped and sent through JSON, and `match`), about 80 s long. Java's peak private working set and CPU as `npm run bench` counts them. Median of 3 interleaved rounds (10,000 tests on one thread: 6); scripts and raw numbers in [docs/research/2026-11-02-java-jit/](../research/2026-11-02-java-jit/README.md).

Java's CPU, peak and wall time:

| Case | No flag (today) | C1 only (`-XX:TieredStopAtLevel=1`) | Two compiler threads (`-XX:CICompilerCount=2`) |
|---|---|---|---|
| 2,000 tests, 1 thread | 13.7 s, 303 MB, 4.6 s | 4.4 s, 144 MB, 3.6 s | 8.3 s, 177 MB, 4.4 s |
| 10,000 tests, 1 thread | 29.3 s, 333 MB, 11.1 s | 13.9 s, 222 MB, 11.9 s | 26.4 s, 263 MB, 14.0 s |
| 10,000 tests, 8 threads | 49.8 s, 617 MB, 6.5 s | 20.2 s, 391 MB, 4.8 s | 28.4 s, 422 MB, 6.7 s |
| 10,000 tests, dry run | 11.5 s, 297 MB, 3.4 s | 2.9 s, 207 MB, 3.3 s | 5.5 s, 221 MB, 3.8 s |
| Heavy JavaScript, 1 thread | 86.4 s, 336 MB, 82.2 s | 316.6 s, 190 MB, 315.5 s | 82.5 s, 335 MB, 76.6 s |
| Heavy JavaScript, 8 threads | 102.2 s, 952 MB, 12.5 s | 637.2 s, 415 MB, 81.6 s | 98.9 s, 864 MB, 12.3 s |

- **C1 only is the lightest on the bench's projects and the worst on heavy JavaScript.** It cut Java's CPU by 53 to 75 % and its peak by 90 to 225 MB, in the same time or less. But Karate's JavaScript engine is an interpreter written in Java, and C1's code runs it about 4 times slower: the heavy-JavaScript suite took 316 s instead of 82 on one thread, 82 s instead of 13 on 8, with Java busy all along.
- **A dry run never meets that case.** It runs no step and no `karate-config.js`, so C1 alone lists the 10,000 tests for a quarter of the CPU, 90 MB less, in the same time.
- **Two compiler threads keep C2 for the runs that need it.** One C1 and one C2 thread cut Java's CPU by 39 % on 2,000 tests, 43 % on 10,000 tests on 8 threads, and 10 % on 1 thread; the peak by 70 to 195 MB. The heavy-JavaScript suite ran in the same time and CPU as today, on 1 and 8 threads, so a long run still gets its hot code through C2. The cost: 10,000 tests on one thread ran about 1 s longer than today in most paired rounds (median of the differences 1.0 s; from 3.7 s shorter to 4.8 s longer), inside the rounds' spread (10.1 to 19.5 s today).
- **Class-data sharing is not taken up again.** The [Java memory research](../research/2026-11-01-java-memory/README.md) measured it: a dry run of 2,000 tests started about 200 ms sooner and peaked 19 MB higher, with a 9.8 MB archive to keep on disk. Memory comes before start time, and C1 already makes the dry run lighter.

## Who and what success looks like

The person running suites all day, with Grace open beside everything else.

Success:
- Listing the tests and running them use clearly less of Java's CPU and memory.
- A run takes no longer than today beyond the noise, including a long suite of heavy JavaScript.

## Goals, non-goals, anti-goals

**Goals:** the behaviour in the Requirements section below.

**Non-goals:**
- A setting to choose the compiler or the number of compiler threads.
- Compile thresholds, the code cache, or a compiler thread count that follows the machine.
- Class-data sharing (see above).
- Changing the heap flags of [the Java memory spec](2026-11-01-java-memory.md).

**Anti-goals** (failure even if everything else works):
- A suite runs slower than today beyond its rounds' spread or the bench's noise, on the bench's projects or a suite of heavy JavaScript.
- Java's peak memory or CPU goes up.

## Constraints

- Flags go on the Java command line, after the `@argfile` and before `-cp` (`buildArgs` in `src/main/karate/command.ts`), after the heap flags.
- `npm run bench` measures it ([docs/specs/2026-10-31-light-and-fast.md](2026-10-31-light-and-fast.md)): `start.tree.*` is the dry run, `run.*` the run. Lowering a limit in `bench/limits.json` is an ordinary commit; raising one needs a decision record.

### What exists today

- `buildArgs` passes `-Xms64m -Xmx2g -XX:+ExitOnOutOfMemoryError -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 -cp …`, the same for the dry run and the run; no compiler flag. Java runs at below-normal priority (#165).

## Approaches considered

- **A. C1 only, everywhere.** The lightest on the bench, but a suite of heavy JavaScript runs about 4 times slower and uses about 4 times the CPU. Rejected: it fails the first anti-goal, and for those suites running lightly too.
- **B. Two compiler threads, everywhere.** Light on runs and safe for heavy JavaScript, but the dry run, which C1 alone does better, took 3.8 s instead of 3.4 (ranges 3.5 to 4.0 against 3.2 to 3.5).
- **C. C1 only for the dry run, two compiler threads for the run (chosen).** Each JVM gets the cheaper flag for what it does: the dry run runs no step, a run may run heavy JavaScript. One flag per mode, chosen where `buildArgs` already tells them apart.
- **D. No flag.** Keeps today's cost.

## Requirements

### R1. The flags

1. A dry run's Java gets `-XX:TieredStopAtLevel=1`; a run's Java gets `-XX:CICompilerCount=2`. Each comes right after the heap flags and before `-Dstdout.encoding`.
2. The values are constants in `command.ts`. Nothing reads them from the project, a setting or the environment.

### R2. The bench

1. `npm run bench -- --release --a <build without the change>` on the reference machine: `run.cpu.java` and `run.cpu.java@10k` are lower; no `run.memory.*`, `run.finishedLag*` or `start.tree.*` measure is worse beyond its noise; the runs pass.
2. A `run.cpu.java*` or `run.memory.java*` limit the bench shows lower is lowered in `bench/limits.json`.

## Design decisions already made

The brief's (#179):
- `-XX:TieredStopAtLevel=1` and fewer compiler threads are measured with the bench's projects and a long suite of heavy JavaScript; class-data sharing with start time.
- The choice follows ADR 0023: running lightly first, then speed.

Mine, open to correction:
- Different flags for the dry run and the run (approach C).
- Two compiler threads, the smallest count Java accepts with both tiers on: one C1, one C2.
- Class-data sharing stays out, on the Java memory research's numbers.

## Acceptance criteria

  Scenario: The dry run compiles with C1 only
    Given a project is open
    When Grace starts Java to list the tests
    Then the command line has "-XX:TieredStopAtLevel=1" after the heap flags and before "-cp"
    And it has no "-XX:CICompilerCount"

  Scenario: A run keeps C2 on fewer threads
    Given a project is open
    When Grace starts Java for a run
    Then the command line has "-XX:CICompilerCount=2" after the heap flags and before "-cp"
    And it has no "-XX:TieredStopAtLevel"

  Scenario: Heavy JavaScript runs no slower
    Given the suite of heavy JavaScript in docs/research/2026-11-02-java-jit/
    When it runs with the run's flags and without, in interleaved rounds
    Then its wall time and Java's CPU are not higher beyond the rounds' spread

  Scenario: The bench shows Java works less
    Given a packaged build with the change and one without it
    When I run "npm run bench -- --release --a <build without the change>" on the reference machine
    Then "run.cpu.java" and "run.cpu.java@10k" are lower than without the change
    And no "run.memory.*", "run.finishedLag*" or "start.tree.*" measure is worse beyond its noise
    And the 10,000-test run passes
