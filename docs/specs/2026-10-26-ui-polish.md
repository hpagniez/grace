# UI polish

Date 2026-10-26. Status: approved. Covers [features](../features.md) F31, F36, F37, F38 and F39.

## Intent

The app works, but five details make it feel unfinished next to a native desktop tool:
- The bottom panel has a fixed height. The HTTP tab (F11) shows about 5 call rows, and a run with 13 calls already needs scrolling (F37).
- The window opens white, then the app paints over it. In dark mode that is a white flash at every start (F39).
- Scroll areas show the default Windows scrollbars: wide, light grey, and light even in dark mode (F38).
- Open… starts wherever Windows puts it, so switching to a sibling project means browsing to it each time (F31).
- Buttons show the arrow cursor (Chromium's default; Tailwind v4 dropped v3's `cursor: pointer` on buttons), and nothing shows that the app is busy (F36).

This batch fixes all five. Each part is small; they share one spec because they touch the same few files (`src/index.css`, `src/main.ts`, `index.html`, `App.tsx`, `BottomPanel.tsx`) and are checked together in the packaged app.

## Who and what success looks like

The walking skeleton's user, iterating on an API suite all day: run, read failures and HTTP calls, fix, run again, sometimes switch to another project.

Success:
- After a run with many HTTP calls, one drag makes the bottom panel tall enough to read them, and the app keeps that height next time.
- The app starts without a white frame, in light and dark mode.
- Scrollbars look like part of the app in both themes and are still easy to grab.
- Open… shows the last project's siblings straight away.
- The cursor says what a control does and when the app is busy.

## Goals, non-goals, anti-goals

**Goals:** the behaviour in the Requirements section below.

**Non-goals:**
- Resizing the tree/details split. It stays a fixed 50/50 (decided in the brainstorm).
- Collapsing the bottom panel, double-click to reset its height, a height per tab or per project.
- A startup screen that stays until the last project's tests are listed (decided in the brainstorm). Discovery shows inside the app as busy.
- Loaders and animations while opening, discovering, saving or running (F29).
- A recent-projects list or Open recent.
- A theme switch inside the app. The app follows the Windows theme, as today.
- Updating the window's background colour when the Windows theme changes while the app runs. The page itself follows the change, as today.
- Arrow-key navigation in lists (F40).

**Anti-goals** (failure even if everything else works):
- A white or wrong-theme frame at start.
- A window that never appears. The app would run where nobody can reach it, and the single-instance lock would turn every new launch into a no-op.
- A panel height that hides the tree and details, or a panel too small to find and drag back.
- Scrollbars so faint that a list that scrolls looks complete. A person would miss HTTP calls or tests below the fold.
- A busy cursor that makes Cancel look unusable.

## Constraints

- No new dependency.
- The Solid 2 rules of `AGENTS.md`.
- `contextIsolation`, `sandbox` and `nodeIntegration: false` stay as they are. The Content-Security-Policy in `index.html` stays as it is: it allows inline styles, not inline scripts, so the startup screen is HTML and CSS only.
- Electron 45 (Chromium supports `scrollbar-width` and `scrollbar-color`), Tailwind CSS 4.3.3. Dark mode is Tailwind's default `dark:` variant, which follows `prefers-color-scheme`, which in Electron follows the Windows app theme (`nativeTheme`).
- Forge dev reloads the renderer once after start. The startup screen may show twice in `npm start`; it must never show white.

### What the app does today

- `src/renderer/BottomPanel.tsx:26`: the panel is a `section` with a fixed `h-48` (192 px). Its three tabs share that height. Its top border is the only line between it and the tree/details area.
- `src/renderer/App.tsx`: a `h-screen` flex column: toolbar, progress bar, filter bar, an optional notice, then `<main class="flex min-h-0 flex-1">` (tree and details, 50/50), then the bottom panel. The app's background (`bg-white dark:bg-zinc-900`) is on this column, not on `html` or `body`.
- `src/main.ts`, `createWindow`: `new BrowserWindow({ width: 1200, height: 800, webPreferences })`, with no `show`, no `backgroundColor` and no `minHeight`, so Electron shows a white window at once, and a short window squeezes `main` (`min-h-0 flex-1`) to nothing. The window is created after the orphan check and before the last project is opened.
- `index.html`: `<div id="root"></div>`, empty until `src/renderer.tsx` runs `render(...)`.
- `@solidjs/web` 2.0.0-rc.18, `render`: it inserts with `element.firstChild ? null : undefined` as the marker, so when `#root` already has children it **appends** after them instead of replacing them. A startup screen placed inside `#root` would stay on screen above the app unless the app removes it.
- `src/main.ts`, `CH.open`: `dialog.showOpenDialog({ properties: ["openDirectory"] })`, with no `defaultPath` and no parent window, so the dialog is not modal to the app. `saveLastProject` runs only after `runner.open` succeeds. `loadLastProject` (`src/main/settings.ts`) returns the saved folder, or null if none is saved or the folder is gone.
- `src/main.ts`, `second-instance`: restores and focuses the window; it never calls `show()`.
- Scroll areas, all `overflow-auto` or `overflow-y-auto`: tree (`Tree.tsx:107`), details pane (`Details.tsx:144`), step log box (`Details.tsx:48`), console (`Console.tsx:26`), History list (`History.tsx:97`), HTTP list (`HttpCalls.tsx:134`), request and response bodies (`CallDetails.tsx:6`), Properties dialog list (`PropertiesDialog.tsx:298`). The console is always dark (`bg-zinc-900`), in light mode too.
- `src/index.css` is `@import "tailwindcss";` and nothing else.
- Cursors: buttons show Chromium's default arrow; Tailwind v4's preflight sets no cursor (v3 set `cursor: pointer`). Disabled controls set `disabled:cursor-not-allowed` in their class strings (`buttons.ts`, `FilterBar.tsx`, `Tree.tsx`, `EnvPicker.tsx`, `CallDetails.tsx`). The Env field is a text `input` with a `datalist`. Checkboxes sit inside `label`s (`FilterBar.tsx:85`, `PropertiesDialog.tsx:377`).
- `AppState.busy` (`src/renderer/reduce.ts`) is true while the Runner holds its one-at-a-time slot: discovering or running. The toolbar treats `run.active || busy` as busy.
- E2E tests stub `dialog.showOpenDialog` in main (`e2e/helpers.ts:75`) with a function that ignores its arguments.

## Approaches considered

Where the panel height is saved (F37):
1. **The renderer's `localStorage`.** About five lines. Read synchronously before the first paint, so the panel never jumps. No IPC. It lives under `userData`, which the e2e tests already point at a fresh folder. Downside: view settings live apart from `settings.json`. **Chosen.** No decision record: losing the saved height is the worst a later change can do.
2. `settings.json` through a new IPC channel and the `ready` replay. One settings file, owned and validated by main. The value arrives after the first paint, so the panel jumps at every start.
3. `settings.json`, with the start value passed through `webPreferences.additionalArguments` and parsed in the preload. One file and no jump, but the most code: read before the window, parse `process.argv`, and an IPC channel to save.

Where Open… starts (F31):
1. **The last project's parent folder.** The app reopens the last project at start, so Open… is mostly for switching to another one, often a sibling. **Chosen.**
2. Inside the last project folder. Fits projects nested in subfolders of the last one.

How long the startup screen stays (F39):
1. **Until the app's UI is drawn.** Discovery of the last project then shows inside the app as busy. **Chosen.**
2. Until the last project's tests are listed. Hides several seconds of JVM start behind a static screen, and needs a path for a failed discovery.

Busy cursor (F36):
1. **`progress`** (arrow with a spinner): says "working, but you can still click". Cancel stays usable. **Chosen.**
2. `wait` (spinner only): says "you cannot click", which is false for Cancel.

How cursors are set (F36):
1. **A few base rules in `src/index.css`**, plus one class on the app's root while busy. Buttons added later get the right cursor too. **Chosen.**
2. A `cursor-pointer` class on every control. Easy to miss one.

How scrollbars are styled (F38):
1. **The standard `scrollbar-width` and `scrollbar-color`**, once, in `src/index.css`. **Chosen.**
2. `::-webkit-scrollbar` pseudo-elements. More control over size and hover, more CSS, non-standard. Only if option 1 looks wrong in the packaged app. Note: Chromium ignores the pseudo-elements on an element that has `scrollbar-width` or `scrollbar-color`, so the two do not mix on one element.

## Requirements

### R1. Resizable bottom panel (F37)

1. A splitter sits at the top of the bottom panel, between the tree/details area and the tab bar. It is a strip at least 6 px high inside the panel's height (not an overlay), so it never covers the tree's or details pane's scrollbars or the tabs, and the panel heights below include it. Its top edge is the panel's existing top border; its background is the tab bar's.
2. Dragging the splitter changes the panel's height: up makes it taller, down makes it smaller. The drag follows the pointer even when it leaves the splitter or the window, and selects no text.
3. The splitter is one tab stop with a visible focus ring. It has `role="separator"`, `aria-orientation="horizontal"`, an accessible name ("Resize bottom panel"), and `aria-valuenow`, `aria-valuemin` and `aria-valuemax` as the panel height in px. Keys, while it has focus:
   - Up: 16 px taller. Down: 16 px smaller.
   - Home: the minimum height. End: the maximum height.
4. Limits: the panel is never smaller than 96 px. It never grows so tall that the tree/details area (`main`) drops below 120 px. The toolbar, progress bar, filter bar and notice keep their natural heights.
5. The window gets a `minHeight` of 480 px, enough for the window frame, the toolbar, progress bar, filter bar on one line, a notice, 120 px of `main` and 96 px of panel. If the top bars are taller still (tag chips wrapping onto several lines), the bottom panel is cut off at the window's bottom edge. The page never scrolls as a whole and the toolbar never leaves the window.
6. The default height is 192 px, today's `h-48`.
7. The saved height is the person's choice. The shown height is the saved height clamped to the limits of R1.4 for the window's current size. A smaller window (or a notice bar appearing) shrinks the shown height without changing the saved one. When there is room again, the panel goes back to the saved height. Only a drag or a key press on the splitter changes the saved height, to the height it shows after the change.
8. The saved height is one value for the whole app, in the renderer's `localStorage`. It is written when a drag ends and after each key press, not on every pointer move. It is read before the panel first paints. A missing, non-numeric, non-finite or below-minimum value reads as 192 px.
9. All three tabs share the one height, as today.

### R2. Open… starts next to the last project (F31)

1. Open… passes the app window as the dialog's parent, so the dialog is modal to the app.
2. Open… passes `defaultPath` = the parent folder of the last opened project (`path.dirname` of `loadLastProject`), read when Open… is clicked. For a project at a drive root (`D:\`), that is the drive root itself.
3. With no last project, or a last project folder that no longer exists (`loadLastProject` returns null), Open… passes no `defaultPath`: the dialog starts where Windows puts it.
4. Only a project that opened successfully counts as the last one, as today (`saveLastProject` after `runner.open`).

### R3. Cursors (F36)

The rules sit in Tailwind's base layer, or match only enabled controls (`:enabled`), so the existing `disabled:cursor-not-allowed` utilities still win. An unlayered `button { cursor: pointer }` would beat them.

1. Enabled buttons show the pointer cursor. This covers every `button`: the toolbar, tabs, tree expand, name and ▶ buttons, HTTP rows and group toggles, History actions, details-pane toggles and the Properties dialog.
2. Checkboxes, and the labels that wrap them, show the pointer cursor.
3. Disabled controls (buttons, inputs, and the labels of disabled checkboxes where the browser allows it) show the not-allowed cursor.
4. Text fields (the Env field, the Properties dialog fields) show the text cursor.
5. The splitter of R1 shows the `row-resize` cursor, while hovered and while dragged. During a drag the whole window shows `row-resize`, so the cursor does not flicker when the pointer moves off the splitter.
6. While the app is busy (`busy` or `run.active`: discovering, or running), the window shows the `progress` cursor wherever no rule above applies. Controls keep their own cursor: Cancel shows the pointer, disabled buttons show not-allowed. The progress cursor goes away as soon as the app is no longer busy.

### R4. Themed scrollbars (F38)

1. Every scroll area of the app uses thin scrollbars (`scrollbar-width: thin`) with a thumb colour from the app's zinc palette and a transparent track. The rule is set once in `src/index.css`, so scroll areas added later get it too.
2. In light mode, the thumb is a mid-light zinc; in dark mode, a mid-dark zinc. In both, it is at least as easy to see against its background as the default Windows thumb, and it stays visible whenever the area overflows (no auto-hide).
3. The console always uses the dark-mode colours, because its background is always dark.
4. Thumbs stay easy to hover and drag. If the standard properties make them too thin or give no hover feedback in the packaged app, use `::-webkit-scrollbar` instead (see Approaches).
5. No light square is left where a horizontal and a vertical scrollbar meet in dark mode. If one is, set `color-scheme` on the root so Chromium paints the native parts dark.

### R5. No white flash at start (F39)

1. The window is created with `show: false` and `backgroundColor` = `#18181b` (zinc-900) when `nativeTheme.shouldUseDarkColors`, else `#ffffff`. These are the app root's two backgrounds.
2. The window shows on `ready-to-show`.
3. The window always appears, even if the page never paints: if loading fails or no `ready-to-show` comes within a few seconds, it shows anyway.
4. `second-instance` shows the window too (`show()`), as well as restoring and focusing it, so a second launch during startup brings the window up.
5. `index.html` holds a static startup screen: the app name and a CSS spinner, centred, with an inline `<style>` whose colours follow `prefers-color-scheme` and match R5.1. It has `role="status"` and an accessible name ("Loading karate-kid"). Under `prefers-reduced-motion: reduce`, the spinner does not spin.
6. The startup screen is gone as soon as the app's UI is drawn, and the page then holds only the app. Because Solid's `render` appends to a `#root` that has children, the startup screen is either outside `#root` and removed after the first render, or `#root` is emptied in a way that never paints a blank frame in the wrong theme.
7. Nothing waits for discovery: the last project opens as today, and the app shows it as busy (R3.6).

## Design decisions already made

- F37 resizes the bottom panel's height only; the tree/details split stays a fixed 50/50.
- The panel height is saved in the renderer's `localStorage`, one value for the app.
- Open… starts in the last project's parent folder.
- The startup screen stays only until the app's UI is drawn.

The spec author's calls: the limits (96 px, 120 px), the 16 px key step and the Home/End mapping; the in-flow splitter strip (R1.1); the 480 px window `minHeight` and cutting off the panel rather than scrolling the page (R1.5); keeping the saved height apart from the shown height (R1.7); the modal dialog (R2.1); `progress` rather than `wait`; `second-instance` calling `show()` and the show fallback (R5.3, R5.4); dark scrollbars in the console; no decision record for `localStorage`.

## Left to the builder

- Component structure: whether the splitter lives in `BottomPanel.tsx` or `App.tsx`, and how the clamp of R1.4 and R1.7 is done. A CSS route exists: `main` with `min-height: 120px`, the panel with the saved height, `flex-shrink` and `min-height: 96px`, so flexbox shrinks the panel when the window is small, and `overflow-hidden` on the app's column for R1.5. The splitter then measures only for `aria-valuemax` and the End key; `aria-valuemax` never goes below `aria-valuemin`.
- Check early, before building on it, that a height written to `localStorage` just before `app.close()` is still there after a restart (Chromium writes `localStorage` to disk lazily). If it is not, flush it on `before-quit` or pick option 3 of the Approaches, and say so in the plan.
- The `localStorage` key name, and how its read is wrapped so a throwing `localStorage` reads as the default.
- Exact zinc tokens for the scrollbar thumbs, within R4.2, and the CSS selectors of R3.
- How the startup screen is removed (R5.6), and how the show fallback of R5.3 is built (`did-fail-load`, a timer, or both) and how long it waits.
- How e2e tests set the colour scheme (Playwright's `colorScheme` launch option emulates `prefers-color-scheme`; the window background check reads `nativeTheme` in main), and how the `showOpenDialog` stub records its arguments.
- Exact wording beyond the strings quoted above.

Resolved by the builder check (2026-10-26). It found one false claim, now fixed: Tailwind v4's preflight sets no cursor on buttons; the arrow is Chromium's default. The spec author's calls from its questions: the window `minHeight` and the cut-off rule (R1.5), the in-flow splitter strip (R1.1), and the base-layer cursor rules (R3). Whether `scrollbar-color` turns off Windows 11 overlay scrollbars is left to the by-hand scrollbar check.
