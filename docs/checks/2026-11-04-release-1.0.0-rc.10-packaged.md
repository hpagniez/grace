### Analysis

Eleven measures are over their limit. They fall in three groups. The per-PR figures below come from each PR's `perf` comment (CI runner, PR mode, 3 rounds); they add up to the moves measured here.

**1. More DOM per drawn tree row: `page.nodes.open` +757 (3100, limit 2845), `page.nodes.open@10k` +775, `page.nodes.run` +690 (7967, limit 7654).**

- Which changes: the step debugger's Debug button on every drawn row (#212: +348 open, +160 run; about 9 nodes per row after its icon was cut to one path), and the one-line filter bar, which gives the tree about 6 more rows (#244: +372 open, +443 run). Small adds: console search (#218, +27/+65), the watch toggle (#245, +15), step comments (#248, +11), Open in VS Code (#217, +12).
- Why over: ADR 0028 raised the open limit by #244's +372 only. #212's +348 fit under the old limit on its own, so together they go over the raised one.
- Can it be fixed: yes. Drawing the Debug button only on the hovered, focused or selected row (or one shared button that moves to the row) would take back most of #212's +348, which brings `page.nodes.open` near 2750, under its limit. #244's rows are the point of #127.

**2. App memory during a run: `run.memory.app` +116 MB (410, limit 322), `run.memory.app@10k` +69 MB (650, limit 607), `page.heap.run@10k` +6 MB (89, limit 88).**

- Which changes: #212 (+30 MB on CI) and #244 (+46 MB on CI; its PR body says +51 MB). The rest is drift of a few MB per PR. On CI, `run.memory.app` went from 188 MB before #212 to about 290 MB after #255; here, 294 to 410 MB.
- Why: #244's PR explains it as a run updating more drawn rows. Six more rows do not explain 46 MB, so a part of that cost is still unexplained; #212 adds the Debug button's tooltip and breakpoint state to each drawn row.
- Can it be fixed: likely, with the same lighter row as in group 1. The #244 share needs a heap snapshot during a run to find what holds the memory.

**3. Frames during a run: `smooth.scroll.run.frame` 9 to 50 ms (limit 25), `smooth.scroll.run.frame@10k` 17 to 67 ms (limit 33), `smooth.run.frame` 17 to 50 ms (limit 33), `smooth.run.fps` 119 to 107 (limit 112), and `smooth.http.idle.frame` 8 to 17 ms (limit 13).**

- Which change: not found yet. The CI runner draws at 60 Hz and its frame figures move in steps of 16 ms, so the per-PR comments cannot place a few ms. The only CI step that matches is #255 (group failures: `smooth.scroll.run.frame` and `smooth.run.frame` 47 to 63 ms), but its base was itself noisy. The likely causes are the same as above: more and heavier rows redrawn on each status update during a run (#212, #244), and #255's grouping on the run's end.
- Why: a frame of 50 ms during a run is a visible stutter on this 120 Hz screen; 1.0.0-rc.9 drew it in 9 to 17 ms.
- Can it be fixed: to be measured. A local bench of `develop` before and after #212, #244 and #255 (PR mode, about 20 minutes each) would place it.

The other measures pass. `start.tree.reused` +430 ms and `run.cpu.app` +1125 ms pass their limits but moved the same way as group 2; `run.memory.java` +60 MB passes (on CI it moves ±70 MB from one run to the next).

Recommendation (the owner decides): no-go. Running lightly is priority 1, and all three groups look fixable: draw the Debug button only where it is used, find #244's run memory, and place the run stutter with a local bench before and after #212, #244 and #255. Then build and bench again.
