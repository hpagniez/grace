# Bench: Java's JIT flags (#179)

Date: 2026-11-02
Builds: A = the `v1.0.0-rc.8` release build, `release/v1.0.0-rc.8` at `fef01e08` (the same app code as `develop` at `9e0c4c86`, plus the version bump), packaged in the release's bench worktree and copied before this run. B = `feature/java-jit` at `3925abfc`: A's code plus `-XX:TieredStopAtLevel=1` on the dry run and `-XX:CICompilerCount=2` on the run, packaged by `npm run bench`.
Machine: the reference machine of the [baseline](2026-10-31-bench-baseline.md) (Windows 11 Pro, Ryzen 7 5800X, 32 GB). The bench logged `windows open at 3140, 246 on DISPLAY1, not the main screen (work area 2560 x 1392 at 2560, 0)`.
Spec: [docs/specs/2026-11-02-java-jit.md](../specs/2026-11-02-java-jit.md).

**Result: Java's CPU during a run falls by 44 % on 2,000 tests and 27 % on 10,000, its peak by 119 and 55 MB, and the tests show 490 to 641 ms sooner.** No measure is worse beyond its noise. The four Java limits are lowered. The bench's `Result: miss` comes from measures that A misses too, by as much or more, on a busy machine (below).

## What was run

- `npm run bench -- --release --a <A>\Grace.exe --label-a "rc.8 fef01e0" --label-b "feature/java-jit 3925abfc"`, from Git Bash, 11:38 to 12:18. Release mode, two builds: one warm-up each, then 5 rounds each in the order a, b, b, a, a, b, b, a, a, b. npm passed the labels through `cmd`, which kept its `^` escapes: the JSON and the report read `^rc.8^ fef01e0^`. No zip given, so `size.zip` reads `not measured`; the change adds no file. The run is in [2026-11-02-java-jit.bench.json](2026-11-02-java-jit.bench.json).
- Machine load before each round: A 13.6 % to 31.3 %, B 6.8 % to 27.0 %. Other sessions were working; no test run or other bench ran. The load is spread evenly over both builds and B is lighter on Java in every round, so the comparison holds, but every absolute number reads higher than on a quiet machine.

## Over a limit, in both builds

- `start.paint.fresh` (A 825, B 671 ms, limit 598), `start.tree.fresh` (A 2,660, B 2,019 ms, limit 1,963) and `run.cpu.app@10k` (A 19,531, B 17,859 ms, limit 17,671): B is better than A on each, and A, the released rc.8 whose own release bench passed, misses them too. The busy machine is the likely cause.
- `smooth.expand.idle.paint@10k` (56 ms, limit 53) and `smooth.expand.idle.frame@10k` (50 ms, limit 47): the same in A and B. They are taken after the tree shows and before Run all, when no Java runs, so Java's flags cannot reach them; #188's record saw the same two over their limits.

## CI's `perf` comment

On the 4-thread CI VM (3 rounds, 2,000 tests), `run.memory.app` read 215.6 MB against 185.3, +30.3 MB against a noise of 23, in every round (A 185.3, 187.2, 183.6; B 217.1, 215.6, 215.0). On the reference machine it did not move (306.6 against 305.2 MB, and 582.7 against 577.3 at 10,000 tests). The flags change only Java. On 4 threads, Java's default of 3 compiler threads falls to 2, and Java's CPU fell by 10.1 s there: the likely link is that the app, with more of the 4 threads free, takes Karate's events in bigger batches. Not checked further.
