## How

The harness is the recheck's [vl-noat.mjs](2026-11-10-gpui-p2-recheck/vl-noat.mjs), one round per call: a calibration launch finds Run all through UI Automation and is killed, then a fresh process that no UI Automation client touches is placed on the second screen, Run all is clicked at the calibrated place, and the app's and Java's CPU are sampled until the run's Java exits. The project is the generated 2,000-test one (`writeBigProject(<dir>, 5)` of `e2e/big-project.ts`).

Three passes, each running GPUI before, GPUI with #351, then Electron, one app at a time. Before each run the machine's total CPU, averaged over 10 s, had to be under 15%.

One change to the harness for this run only: the app's stderr went to a file and its exit was logged, because in a run stopped on 2026-11-11 GPUI Grace was gone before sampling in 3 of 8 launches. Nothing of the kind happened here: GPUI Grace wrote nothing to stderr in its 18 launches and ended only when the harness killed it. That run shared one Cargo target folder between the two builds; this one gave each its own.

## What this does not show

- The numbers are higher than the recheck's for the builds that did not change much (Electron 4,922 ms against 4,156 ms, GPUI before #351 6,078 ms against 5,438 ms). The commits differ, and the machine was nearer the 15% load line. Compare within this record, not across records.
- Pass 3's GPUI-before peak memory (56.2 MB against 88 to 89 MB) was not explained. The median is not moved by it.
- The harness does not read the screen during the measured run: that the results, progress bar and marks still show as the run goes is proved by #351's own tests, not here.
- With a UI Automation client attached GPUI Grace builds its accessibility tree and does not cache its panes; that case was not measured again (6,922 ms in the recheck).
