### Analysis

One measure missed: `start.paint.fresh`, the first paint of a start on a new profile, at 828 ms against its limit of 598 (1.0.0-rc.8: 512). Every other measure passes, and six are better than their limits: both sizes (#150), and Java's memory and CPU in both projects (#179).

- **How much it moved:** +316 ms in the median of 5 rounds. The rounds split in two groups, in both builds: a start paints at about 500 ms, or now and then at 800 to 1100 ms. 1.0.0-rc.9's rounds were 510, 950, 492, 828 and 916 ms (3 slow); 1.0.0-rc.8's were 1114, 556, 483, 512 and 491 ms (1 slow). The median fell on a slow round for 1.0.0-rc.9 only.
- **Which change caused it:** none found. Measured again right after the bench, on the same machine and builds, with only this start (the bench's own `startApp` and `startTimes`, the same 2,000-test project, a new profile each time), 20 times per build, alternating: 1.0.0-rc.8 median 496 ms, 1 start over 700 ms; 1.0.0-rc.9 median 510 ms, 2 starts over 700 ms. The +14 ms is within the round-to-round spread, and the slow starts are as rare in one build as in the other.
- **Why:** a start on a new profile now and then takes about 400 ms more to paint, in either build; the bench's 5 rounds caught three of those for 1.0.0-rc.9. Nothing in the changes since 1.0.0-rc.8 runs before the first paint on a new profile only: #179 changes Java's flags, #150 only removes locale files (and the measured fresh starts of the two builds match), and #81 and #64 change the toolbar and what is read when a project opens. `start.paint.reused`, the same start on a profile that exists, is 396 ms against 403.
- **Can it be fixed:** there is nothing in this release to fix. The slow fresh starts are worth their own look, since they also happen in 1.0.0-rc.8; and with 5 rounds a measure with two groups can fall either way.
