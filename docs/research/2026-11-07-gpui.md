# GPUI: Rust and Zed's GPU UI as a replacement for Electron and Solid (#152)

Date 2026-11-07. A desk study: public sources, the crates.io registry, Grace's own records and its code on `develop` at `dc88524`. Nothing was built or measured. This session ran on Linux, away from the reference machine of `bench/limits.json`, so every GPUI number below is someone else's, on another machine, for another app. It answers the "native UI" row of [#152](https://github.com/hpagniez/grace/issues/152) on paper, so that a prototype, if one is built, starts from the right questions.

## Verdict: no-go for a migration today, go for a measured prototype

Stay on Electron and Solid. GPUI is the first candidate that could make Grace much lighter: unlike Tauri, it drops the browser engine, and the numbers others have published point to a large cut in Grace's own memory and size. But a move rests on numbers nobody has taken for an app like Grace, it means rewriting all of Grace in Rust, and GPUI itself has no stable release and no single maintained line outside Zed.

- **What could be gained.** Others measured GPUI windows at about 20 to 25 MB private working set idle, a start to first frame of about 260 ms, and an 8.5 to 11 MB exe ([Measured by others](#measured-by-others)). Grace today reads 155 MB idle, 299 MB in the app process tree during a 2,000-test run (577 MB at 10,000), a first paint at 529 ms and a 218.7 MB zip, of which 158 MB is Electron. If a GPUI Grace kept even half of that gap, it would win on all three of Grace's priorities, in order.
- **What it cannot touch.** Java. During a run, Karate's JVM takes 307 MB at 2,000 tests and 495 MB at 10,000, about half of Grace's run memory. The bundled JRE and Karate jar are 60 MB of the zip. Neither changes with the UI.
- **What it would cost.** A full rewrite: about 14,600 lines of TypeScript and 29,000 lines of its tests, the 30 e2e spec files, the bench's page probes, the test tools of ADR 0004 and ADR 0005, and the UI conventions of AGENTS.md. Tauri, judged too costly in [#106](https://github.com/hpagniez/grace/issues/106), kept the renderer; GPUI keeps nothing but the Java listener ([The cost](#the-cost)).
- **What is risky.** Zed slowed GPUI work outside its own needs in 2026, and the official `gpui` crate has not been published since 2025-10-22. Apps outside Zed build on snapshots and forks ([GPUI today](#gpui-today)). One published benchmark read GPUI using 0.86 % of a core while idle, which would break "idle costs nothing" if it held for Grace ([Risks](#risks)).

**Update, same day: the prototype is built.** [2026-11-07-gpui-prototype](2026-11-07-gpui-prototype/README.md) has Grace's main screen in GPUI, measured against Grace on Linux. It is lighter in memory (145 MB against 210 MB idle, 155 MB against 352 MB during a run), size (25 MB against 279 MB) and start (143 ms against 305 ms). Idle CPU is not lower, and without a GPU it is less smooth. The verdict holds until the Windows run of #267. No decision record: a go would need one that supersedes ADR 0001, ADR 0004 and ADR 0005. A no-go keeps them.

## Did Discord and Shopify move to GPUI?

Discord did, Shopify did not.

- **Discord: yes, announced, not shipped.** On 2026-11-04 Discord's CTO, Stanislav Vishnevskiy, said on X that Discord is rebuilding its client in Rust: "Electron goes away, and so does React Native, mobile keeps native UI but shares app code" through Rust, and "it's not Tauri, it's GPUI" ([X post](https://x.com/svishnevskiy/status/2118081920194203799), [Windows Latest](https://www.windowslatest.com/2026/11/05/discord-is-killing-its-electron-app-that-can-eat-4gb-of-ram-on-windows-11-and-the-rust-rebuild-uses-just-290mb/)). The reason given is that Discord has used Rust since 2018 in its infrastructure, voice and parts of today's client, and the whole client in Rust was "the holy grail". The early Windows build, "Phoenix", has no release or test date. Its widely quoted 290.2 MB of RAM comes from one screenshot with two accounts signed in, with no stated workload, so it is not a benchmark ([Windows Forum](https://windowsforum.com/news/discord-phoenix-rust-and-gpui-replace-electron-on-windows-but-290mb-ram-claims-need-testing.450993/)). Embedded content such as videos will still use the system webview.
- **Shopify: no.** On 2026-09-10 Shopify said it is moving its mobile apps from React Native to native Swift and Kotlin ([Shopify Engineering](https://shopify.engineering/back-to-native), [InfoQ](https://www.infoq.com/news/2026/09/shopify-drops-react-native/)). The post does not mention Rust, GPUI or Electron. Its reason is worth noting for Grace anyway: coding agents made writing a feature twice cheap enough that sharing one implementation stopped paying off, and the Shop app was rebuilt in 12 weeks. Shopify said React Native was not slow; performance was not the reason.

What Discord's move does for Grace: it gives GPUI a second large user beside Zed, which may bring maintenance and fixes on Windows. It is two days old, so nothing it has published yet is evidence about memory or CPU.

## What Grace runs on today

| Layer | Today | Size on `develop` |
|---|---|---|
| Shell | Electron 45.1.0, packaged by Forge 8 into a Windows zip | 158 MB of the 218.7 MB zip |
| Main process | Node, TypeScript: spawns Karate, tails `karate-events.jsonl`, history, settings, secrets (`safeStorage`), updater, watch | `src/main`: 5,826 lines, 12,348 of tests |
| Renderer | Solid 2 RC, Tailwind 4, IBM Plex, lucide, virtual tree | `src/renderer`: 7,530 lines, 15,565 of tests |
| Shared | Types and logic both sides use (tags, env, history, threads, flaky) | `src/shared`: 1,205 lines, 1,340 of tests |
| Java | Bundled Temurin 21 JRE, Karate 2.x jar, `listener/grace/DebugListener.java` | 60 MB of the zip |
| Tests | Vitest (ADR 0005), Playwright `_electron` e2e (ADR 0004), the bench over CDP (ADR 0023) | 30 e2e specs, `bench/` 2,858 lines |

The [Tauri spike](2026-10-29-tauri-spike/README.md) found that a different browser engine does not help: WebView2 is Chromium, and it used 8 to 10 MB more idle and painted 124 to 134 ms later. The [idle CPU note](2026-10-31-idle-cpu-shown.md) found Grace idle at about 0.23 s of CPU a minute once shown, of which Electron with a blank page is 63 ms, and the rest Chromium's own housekeeping for a page of about 2,300 nodes. So the remaining room is in the engine itself, which only a native UI removes.

## GPUI today

GPUI is the UI framework Zed is written with: Rust, drawn on the GPU (Metal on macOS, DirectX 11 on Windows, Vulkan on Linux), with a retained tree of entities and views and a Tailwind-like styling API. Windows is its newest platform: Zed shipped there in 2025.

- **No stable release, and the line is split.** On crates.io, read on 2026-11-07:

  | Crate | Latest | Published | What it is |
  |---|---|---|---|
  | `gpui` | 0.2.2 | 2025-10-22 | Zed's own; not published since |
  | `gpui-pre` | 0.3.11 | 2026-11-02 | Snapshots of Zed's GPUI (`zed@f816e1f`), published by a Longbridge maintainer |
  | `gpui-kit` / `gpui-component` | 0.9.0 | 2026-11-02 | Longbridge's component set on `gpui-pre`, weekly releases |
  | `gpui-ce` | 0.3.0 | 2026-10-20 | Community fork |
  | `gpui-unofficial` | 1.28.0-pre | 2026-11-05 | Another fork |

- **Zed's priorities.** A Zed maintainer wrote on Zed's Discord that GPUI development "is getting some major brakes put on it" in 2026 and that anything not "directly related to Zed's use case" would wait ([quoted on Hacker News](https://news.ycombinator.com/item?id=47003569); second-hand, no official post found).
- **Components.** GPUI itself ships primitives. [GPUI Kit](https://github.com/longbridge/gpui-component) (Longbridge, used in its shipped Longbridge Pro app) adds 75 components, among them inputs, virtual lists with variable row heights, data tables, dock layouts, tooltips, Markdown and a code editor. It claims AccessKit accessibility and headless UI integration tests. Grace's tree, details panel, console and HTTP inspector would map onto these.
- **Accessibility.** Electron gives Grace the Windows accessibility tree for free. `gpui-pre` 0.3.11 has AccessKit roles, labels, states and actions (its `a11y` example), set by hand on each element; GPUI Kit builds them into its components. Grace's PR checklist asks for a UI "labelled for screen readers", so this is a gate for a prototype, not a footnote. (Corrected after the prototype: this note first said upstream support was limited.)
- **Agents.** Grace is built mostly by AI agents. GPUI's API changed a lot between Zed releases, few apps outside Zed use it, and its docs are mostly its source, so agents will know it far less well than TypeScript and the web. AGENTS.md already needs a "Solid 2 rules" section for a much smaller gap.

## What would change, by priority

1. **Run lightly.**
   - Memory: the likeliest gain. Electron's floor (browser, GPU and renderer processes) goes away. During a run, the app's share (299 MB at 2,000 tests, 577 MB at 10,000) holds the tree, the results and the page; a Rust app holds the same data in far less, but how much less is unknown until measured. Java's share does not move.
   - Idle CPU: unknown, and possibly worse. One benchmark read GPUI at 0.86 % of a core idle, about 0.5 s a minute, against Grace's 0.23 s today; another read `gpui-fast` at zero. GPUI redraws only when a view is notified, but Grace would have to prove it never wakes, shown and minimised.
   - Smoothness: GPUI draws at the display rate and handled a 100,000-row virtual list cheaply, but one benchmark saw 46 fps on a scrolled 1,000-row list. Grace's run view updates rows every 100 ms during a run, which is that kind of load.
2. **Be fast.** Start to first frame was 259 ms in one benchmark, against Grace's 529 ms first paint. The tree's time (1,782 ms fresh) is mostly the Karate dry run, which does not change.
3. **Be small.** The zip would go from 218.7 MB to about 70 to 75 MB: the 60 MB of Java plus a 10 to 20 MB exe. The Tauri spike's Rust build reached 62.5 MB the same way.

## The cost

- **Main process into Rust.** Everything the Tauri spike's option 1 listed: about 5,800 lines of `src/main` (now twice what that spike counted) and their tests, the Karate spawn rules, `taskkill`, event tailing, history, settings, the updater of ADR 0019, `safeStorage` replaced by DPAPI or Credential Manager, and file watching.
- **Renderer into Rust.** 7,530 lines of Solid and 15,565 of tests, rebuilt in GPUI views: the virtual tree, the HTTP inspector, the console, trends, the step debugger's controls, settings. The UI conventions of AGENTS.md (semantic tokens in `src/index.css`, `palette.test.ts`, `tokens.test.ts`, `Tooltip`, `StatusMark`, `Icon`) would be rewritten as a GPUI theme and components. IBM Plex and lucide's SVGs carry over.
- **Tests.**
  - Vitest goes: unit tests become `cargo test`, UI tests GPUI's `TestAppContext` or GPUI Kit's headless windows.
  - Playwright goes: there is no DOM and no CDP. The 30 e2e specs would drive the app through Windows UI Automation, which only works as far as the accessibility tree is complete, or through a test hook built into the app.
  - The bench: its start, memory, CPU and size parts carry over, since they read processes and files. Its Smooth probes and `page.*` measures run over CDP and would need a GPUI-side probe. Comparing the two stacks on Smooth would not be like for like.
- **Build and CI.** A Rust toolchain on the Windows runners, longer cold builds than Vite, and a `perf` job that builds two Rust trees. SignPath still signs one `Grace.exe` (ADR 0024).
- **One language, at least.** Unlike Tauri, a full GPUI Grace has no TypeScript left, so `src/shared` does not split. That is the one cost GPUI has lower than Tauri.

The rule of [No backward compatibility](../../AGENTS.md#no-backward-compatibility) helps: before 1.0.0, settings, history and the updater's contract can change. After 1.0.0, the updater's contract cannot change without a decision record, so a move gets more expensive after the first stable release.

## Risks

| Risk | Why it matters | What would reduce it |
|---|---|---|
| No stable GPUI; split between `gpui-pre`, forks and Zed's tree | API breaks on every update; a fork can stop | Pin one snapshot through GPUI Kit; budget for its upgrades as Grace does for Solid's RC |
| Zed slowing GPUI work outside Zed | Windows bugs that Zed does not hit may not get fixed | Discord's move may change this; wait for its fixes to land upstream |
| Idle CPU above zero | Breaks the first rule of ADR 0023 | Measure shown and minimised in the prototype before anything else |
| Accessibility | A regression from Electron, and e2e depends on it | Check the prototype's tree with Accessibility Insights and Narrator |
| Agents know GPUI poorly | Slower, buggier PRs in a repo built by agents | Measure it: have agents build the prototype and count review rounds |
| A rewrite of everything at once | Months with no features | Only after a measured go; Shopify's 12-week rebuild with agents is a data point, not a promise |

## A prototype that would decide it

What #152 asks for, in GPUI: a throwaway app in its own folder under `docs/research/`, not kept in the build. It needs the home screen and the test tree of the bench's 2,000-test project, with Run all and live progress from `karate-events.jsonl`, on GPUI Kit's pinned `gpui-pre`. It needs no history, settings, secrets or updater.

Measure it on the reference machine against Grace at the same commit, with the bench's process and size parts and 5 rounds:

- `idle.memory`, `idle.cpu.shown`, `idle.cpu.minimised`
- `run.memory.app`, `run.cpu.app`, at 2,000 and 10,000 tests
- `start.paint.*` as first frame, `start.tree.*`
- `size.zip`, `size.unpacked`
- smoothness from its own frame timer during Run all, against `smooth.run.fps`
- the accessibility tree, read with Accessibility Insights

A go would need, at least: idle CPU no higher than Grace's, shown and minimised; idle and run memory of the app clearly lower, beyond noise, at both sizes; no slower start; and a usable accessibility tree. Then a decision record that supersedes ADR 0001, ADR 0004 and ADR 0005 and a migration plan. Anything less is a no-go, and #152 moves on to the Electron empty-page floor and the `en-US`-only locale cut the Tauri spike left open.
