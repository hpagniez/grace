# Stack research: Electron + Solid 2 + TanStack + Tailwind (karate-kid)

Checked on 2026-10-24 against the npm registry (`registry.npmjs.org` dist-tags, peerDependencies and publish dates), GitHub releases and official docs. Versions below are what npm returned that day.

Proposed stack: Electron + TanStack Start + SolidJS v2 RC + Tailwind CSS.

**Bottom line:** keep Electron, Solid 2 RC (pinned), TanStack **Router** (not Start) and Tailwind v4. Drop TanStack Start: the Electron main process is already the Node backend, so Start's server layer only adds weight.

---

## 1. SolidJS v2: status, breaking changes, router and meta-framework support

### Status

- `solid-js@2.0.0-rc.18` (published 2026-10-23) is on the `next` tag. `latest` is still `1.9.17` (2026-10-07).
- `@solidjs/web@2.0.0-rc.18` is the new DOM renderer and is required alongside `solid-js`.
- The v2 site says it is a **release candidate**: "APIs may change before the stable release". Packages from the coordinated RC must use compatible versions.
- No stable date has been announced. RCs ship about weekly (rc.16 to rc.18 in October).
- SolidStart reached a stable 2.0 in September 2026 and then went into maintenance mode. Solid 2's "Start mode" in `@solidjs/vite-plugin` replaces it (InfoQ).

### Key breaking changes vs 1.x

Source: v2 migration guide.

**Packages and imports**
- `solid-js/web` becomes `@solidjs/web`.
- `solid-js/store` is merged into `solid-js`.
- Set `jsxImportSource` to `@solidjs/web`.
- `vite-plugin-solid` is replaced by `@solidjs/vite-plugin`. That plugin is at `3.0.0-next.51` and peers `vite ^8 || ^9`.
- The Babel preset is gone. Compiler natives ship as `@solidjs/compiler-*`.

**Signals**
- Setter writes are staged until the next microtask.
- `batch` is removed. Call `flush()` when you need a synchronous read.
- Writes inside component bodies or memos are rejected in development.

**Effects**
- `createEffect` is split into a tracked compute function and an untracked apply function.
- `onMount` becomes `onSettled`.
- `on` is removed.
- `initialValue` is removed from `createEffect` and `createMemo`.

**Async**
- `createResource` is removed. Use async `createMemo`.
- `Suspense` becomes `Loading`, and `ErrorBoundary` becomes `Errored`.
- `startTransition` and `useTransition` are removed.

**Stores**
- Setters receive a draft. Path setters and `produce` are removed.
- Renames: `mergeProps` to `merge`, `splitProps` to `omit`, `unwrap` to `snapshot`, `createSelector` to `createProjection`.

**JSX**
- `Index` becomes `<For keyed={false}>`, and `For` children receive accessors.
- `Context.Provider` becomes the context component itself.
- `use:` directives, `classList`, `on:`, `attr:` and `bool:` are removed.
- Lowercase `onclick` is now a plain attribute. Use `onClick`.

- TanStack announced Solid 2 support (beta, "intentionally early") on 2026-04-10. It has tracked each Solid RC since.
- TanStack Start itself is marked stable, but its Solid 2 line is still RC.
- The v2 SolidStart migration page still says "TanStack Solid Router 1", which is stale wording. The `2.0.0-rc.*` line is the one that peers Solid 2.

**Recommendation:** if you want Solid 2, use `solid-js@2.0.0-rc.18` + `@solidjs/web@2.0.0-rc.18` + `@tanstack/solid-router@2.0.0-rc.9` + `@solidjs/vite-plugin@3.0.0-next.51`.

- Fallback if the ecosystem gaps in §5 hurt: `solid-js@1.9.17` + `@tanstack/solid-router@1.170.43`.

**Risks**
- RC churn: the APIs may still change.
- Exact peer pins in third-party libraries. For example, Kobalte alpha peers exactly `2.0.0-rc.16`.
- AI agents were trained mostly on Solid 1. They will write `createResource`, `onMount`, `Suspense`, `solid-js/web` and `splitProps`. Put a Solid-2 rules section in AGENTS.md.

## 2. TanStack Start inside Electron

### Official support

- No official docs or guides cover Electron. The Start overview never mentions desktop.
- Start is server-first: SSR, server functions and server routes.
- SPA mode (`tanstackStart({ spa: { enabled: true } })`) only prerenders a `/_shell.html` shell. Server functions and server routes **still need a running server**.

### Realistic options

1. **TanStack Router + Vite only, as a pure SPA. Recommended.**
   - The renderer is a static Vite build loaded with `loadFile` or a custom `app://` protocol.
   - Use `createHashHistory()` or memory history so that `file://` does not break deep links.
   - All "backend" work (spawning Karate/Java, the file system, watching reports) lives in the main process behind typed IPC.
   - This gives the fewest moving parts and the smallest attack surface. You keep file-based routing via `@tanstack/router-plugin` (1.168.48).
2. **Start in SPA or static-prerender mode, with all data over IPC.**
   - You pay for Start's server build and plugin, then use none of its server features.
   - No benefit over option 1.
3. **Run the Start server inside the main process.**
   - Community examples do this:
     - `spa5k/tanstack-start-electron` imports the SSR handler into main and serves it on `app://` with no TCP port.
     - `cheriot/electron-tanstack-demo` runs a loopback server protected by a shared secret and CSP.
   - This works, but it duplicates IPC with HTTP or server functions and needs auth on the local port.
   - Both examples are React, with 0 to 9 stars. None of them is Solid 2.
   - Only worth it if the same app must also ship as a web app.

**Recommendation:** option 1. Use `@tanstack/solid-router` (2.0.0-rc.9 for Solid 2) inside an electron-vite or Forge Vite renderer. Skip Start.

**Tradeoff:** you lose server functions and SSR, and you never need them in a desktop app.

**Risks**
- With option 3 you take on Start + Solid 2 RC + Electron at once, with no reference project. That is the highest risk in the proposed stack.

## 3. Tailwind CSS

- Current major is **v4**: `tailwindcss@4.3.3` and `@tailwindcss/vite@4.3.3`. v3 is kept under the `v3-lts` tag (3.4.19).
- Setup:
  - Install: `npm i tailwindcss @tailwindcss/vite`.
  - Add `tailwindcss()` to the renderer `plugins` in the Vite config.
  - Put `@import "tailwindcss";` in the CSS entry.
  - There is no `tailwind.config.js`. Configure in CSS with `@theme`.
- With electron-vite, add the plugin under `renderer.plugins`. With Forge, add it in `vite.renderer.config.ts`.
- Risk: low. It is renderer-only and independent of Solid's version.

**Sources**
- https://tailwindcss.com/docs/installation/using-vite
- https://www.npmjs.com/package/tailwindcss

**Recommendation:** Electron Forge 8 with `@electron-forge/plugin-vite`.
- One official toolchain covers dev, package, make and release.
- Its Vite plugin is now stable on Vite 8, which `@solidjs/vite-plugin` 3 requires.
- To add Solid 2, swap the renderer plugin to `@solidjs/vite-plugin`.

**Alternative:** electron-vite 6 + electron-builder 26.
- Better dev experience: single config and a more mature HMR and restart loop.
- Richer auto-update.
- Two tools instead of one.

Both are fine. Pick one and do not mix them.

**Risks**
- Forge's Vite plugin only left experimental a month ago.
- The electron-vite Solid template needs manual migration to Solid 2 (plugin swap, `jsxImportSource`).

**Process-spawning notes**
- Kill the process tree on Windows with `taskkill /T /F` or the `tree-kill` package.
- For live progress, tail `karate-events.jsonl` (`-f html,karate:jsonl`), not stdout. See [karate-core.md §19](../inventory/karate-core.md#19-integration-surface-for-a-gui).

**Recommendation**
- **UI primitives:** Kobalte 2 alpha, pinned with an `overrides` entry for `solid-js` and `@solidjs/web`. If it breaks, fall back to Ark UI 6 next.
- **Editor:** CodeMirror 6 with the legacy gherkin mode.
- **Virtual list:** `@tanstack/virtual-core` with your own adapter.
- **Processes:** `node:child_process` in main.
- **IPC:** hand-rolled typed preload. Move to oRPC only if the channel count grows.

**Risks**
- Every Solid UI library is either alpha or unverified on Solid 2.
- Expect to write small adapters, and budget for one RC-bump break per month.

**Recommendation:** plain Markdown now. Add Starlight later only if a public docs site is needed: it consumes the same files.

The adopted layout is recorded in [ADR 0002](../decisions/0002-plain-markdown-docs.md).

**Conventions**
- **ADRs:** MADR 4.0.0, stored as `docs/decisions/NNNN-title-with-dashes.md`.
  - YAML frontmatter: `status` (proposed | accepted | rejected | deprecated | superseded by ADR-NNNN), `date`, `decision-makers`.
  - Sections: Context and Problem Statement, Considered Options, Decision Outcome (+ Consequences, Confirmation).
  - Use the "minimal" template so agents keep them short.
  - The first ADRs should record this stack choice and the "no TanStack Start" decision.
- **Specs:** use Markdown with EARS-style requirements plus Gherkin acceptance criteria.
  - Agents handle both well.
  - Gherkin is the same language as Karate `.feature` files, so specs can become real tests.
- **Feature inventory:** keep one Markdown table that agents update in the same PR as the feature.

**Risks**
- Docs drift when agents skip them. Mitigate with a rule in AGENTS.md: "update docs/features.md and the spec in the same change".
- Optionally add a CI check that every feature id has a spec file.

## Biggest risks overall

1. **Solid 2 is an RC and its ecosystem is thinner.**
   - The core RC and TanStack Router RC are coordinated, but UI libraries are alpha (Kobalte, with exact peer pins) or untested (Ark, virtua).
   - The virtual list and the editor wrapper need hand-written adapters.
   - Pin exact versions and upgrade the whole set together.
2. **TanStack Start + Electron + Solid 2: no official path and no Solid example.**
   - Avoid it. Router-only removes the risk.
3. **AI agents default to Solid 1 idioms.**
   - Enforce the Solid 2 rules in AGENTS.md, and lint for the `solid-js/web` and `solid-js/store` imports.
4. **Fresh tooling majors:** Forge 8, electron-vite 6 and Vite 8 all came out in the last 1 to 2 months.
5. **Windows process-tree kill for the Java process.**
   - A plain `child.kill()` can leave the JVM running.
